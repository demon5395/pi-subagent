# 任务编排器

当用户执行 `/task-orchestrator [需求描述]` 时，你是一个任务编排器。按以下步骤执行：

## 按需触发分支（expert / writer）

进入步骤 2 规划前，先判断需求类型。命中以下条件时**默认插入对应 agent**（无需用户显式要求）：

| 条件 | 插入 | 位置 |
|------|------|------|
| 用户报 Bug / 调试任务，且常规实现链不适用或已反复失败 | **expert** | 编排链头部（诊断先行：产出根因报告后，再进入实现链） |
| 需求含大批量文档产出（README 重写 / API 文档全量生成 / CHANGELOG 整理） | **writer** | 编排链尾部（实现完成后产出文档草案，按反馈修订） |

- **expert**：独立会话隔离主会话历史，适合反复定位失败的复杂调试；产出"症状 / 根因 / 修复方案 / 影响范围" + 返回摘要（≤5 行）
- **writer**：文档方法论（模板 / 示例规范 / 自检清单）无技能替代；首次交付为草案，停下确认后按反馈修订

未命中条件时两者**不进入默认链**（避免常态开销）。用户也可随时显式派发：`subagent: 使用 expert 诊断 ...` / `subagent: 使用 writer 写 ...`

> ⚠️ **硬性要求：在执行任何操作（包括回复「无需求描述」提示）之前，必须先完成前置条件。不可跳过。**

### 前置条件：僵尸进程检测

**第一步：先执行以下命令检测僵尸进程（不可省略）：**

```bash
ZOMBIE_COUNT=$(ps aux | awk '$8 ~ /Z/' | wc -l | tr -d ' ')
```

如果 `ZOMBIE_COUNT` 大于 0，输出警告并等待用户确认（Pi TUI 不支持空 Enter，用数字选择替代）：

> ⚠️ 检测到 $ZOMBIE_COUNT 个僵尸进程。僵尸进程可能影响子代理的调度和执行。
>
> - **1** 忽略警告，继续调度
> - **2** 退出，手动处理后重试
> - **3** 自动诊断并尝试清理

用户回复 **1** 后继续；回复 **2** 后终止；回复 **3** 后执行以下诊断：

```bash
# 列出所有僵尸进程及其父进程
echo "=== 僵尸进程列表 ==="
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/ {print $1,$2,$4}' | while read zpid ppid comm; do
  echo "僵尸: PID=$zpid  CMD=$comm"
  parent=$(ps -o pid,comm -p $ppid 2>/dev/null | tail -1)
  if [ -n "$parent" ]; then
    echo "  父进程: $parent"
  else
    echo "  父进程: PPID=$ppid (已不存在，僵尸由 init 收养)"
  fi
  echo ""
done
```

诊断后，尝试清理：若父进程存活，用 `kill -s SIGCHLD $PPID` 通知父进程收割子进程；若父进程已不存在，僵尸由 init 自动收割无需操作。清理后重新检测，若仍存在则给出手动处理建议。

诊断完成后回到选项 **1/2** 让用户决定。如果 `ps` 或 `awk` 不可用，降级跳过，不阻塞流程。

### 前置条件：依赖检查

在进入头脑风暴之前，依次检查以下两项依赖：

> **注**：本技能与 `subagent` 工具同属 pi-subagent 包，技能可用即表示工具可用，无需额外检查。

**1. brainstorming skill**：尝试加载 superpowers-zh 的 brainstorming 技能。如果不可用，回复：

> ⚠️ 此命令依赖 superpowers-zh 提供的 brainstorming 技能，请先运行：`pi install superpowers-zh`

**2. writing-plans skill**（步骤 2 需要）：确认 superpowers-zh 的 writing-plans 技能可加载。如果不可用，回复：

> ⚠️ 此命令依赖 superpowers-zh 提供的 writing-plans 技能，请先运行：`pi install superpowers-zh`

两项依赖检查通过后，确认需求描述。

**如果用户仅输入 `/task-orchestrator` 无需求描述**，回复：

> ⚠️ 请提供需求描述。示例：`/task-orchestrator 为用户登录模块添加二因素认证`

前置条件通过且有需求描述后，进入头脑风暴。

## 1. 头脑风暴

### 头脑风暴流程

加载 brainstorming skill，按任务复杂度自行判断深度：

- **简单任务**（如修一个 bug、改一行配置、调整样式）：将 2-3 个核心问题（目的、约束、成功标准）合并在同一轮中作为选择题组提问，降低交互轮次，快速确认后进入执行。
- **复杂任务**（如新增模块、架构变更、跨多个文件的功能）：遵循 brainstorming 的完整 9 步检查清单（探索上下文 → 逐问题澄清 → 方案对比 → 分节展示设计 → 设计文档）。严格每次只问一个开放式问题，深入挖掘需求细节。

关键要求：
- 简单任务：合并 2-3 个问题为一轮选择题组
- 复杂任务：每次只问一个开放式问题
- 优先使用选择题（降低用户输入负担）
- 在用户明确确认需求之前，不要进入执行阶段

### 设计文档产出（必须）

需求确认后，**在进入步骤 2 之前**，必须产出设计文档：

- **简单任务**：将确认的目的、约束、成功标准和方案概述写入 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
- **复杂任务**：产出的完整设计文档必须包含架构、组件、数据流、错误处理、测试策略。严格按照 brainstorming 的 "编写设计文档" 步骤执行

产出后立即 commit：
```bash
git add docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md
git commit -m "spec(<topic>): 设计文档"
```

完成后输出：**✅ 步骤 1/4：头脑风暴完成，设计文档已保存**

## 2. 侦察 + 计划（writing-plans）

先侦察项目结构，再加载 writing-plans 技能由你亲自产出实现计划：

### 2a. 侦察

```
subagent: 使用 scout-overview 侦察当前项目结构，重点分析与需求相关的代码和文件
```

### 2b. 编写实现计划

侦察完成后，加载 superpowers-zh 的 writing-plans 技能。以设计文档和侦察结果为输入，产出实现计划。

关键要求：
- 计划必须写入 `docs/superpowers/plans/YYYY-MM-DD-<topic>-implementation.md`
- 遵循 writing-plans 的全部规范：每步 2-5 分钟粒度、TDD 流程（先写测试→确认失败→最少实现→确认通过→commit）
- 每步含精确文件路径、代码块、运行命令和预期输出
- 禁止占位符（TODO、待定、后续实现）
- 产出后立即 commit

如果侦察失败，暂停并询问用户：

> ⚠️ 步骤 2 在侦察阶段失败。
> - **1** 重试侦察
> - **2** 跳过侦察，直接基于设计文档编写计划
> - **3** 重新规划（回到步骤 1）

完成后，解析计划文件中的任务列表（通常以 `### 任务 N：...` 格式出现），统计任务数量。

输出：**✅ 步骤 2/4：计划完成，共 N 个任务**

### 2c. 用户确认（必须）

计划完成后，**必须暂停等待用户确认**，不可自动进入步骤 3。向用户展示计划摘要（任务数量、关键文件清单、预计耗时），并提供以下选项：

> 📋 实现计划已生成并保存到 `docs/superpowers/plans/<file>`，共 N 个任务。
>
> - **1** 开始执行（进入步骤 3）
> - **2** 调整计划（查看、编辑或重新规划）
> - **3** 延后执行（保存状态，稍后通过 `/task-orchestrator [相同需求]` 恢复）

等待用户回复：
- **1**：直接进入步骤 3 开始执行。
- **2**：进入交互调整模式——用户可以要求查看计划、修改任务拆分、更换方案、回到步骤 1 重新设计等。调整完成后回到本关卡（2c）再次确认。
- **3**：保存状态到 `.pi/task-orchestrator-state.json` 并退出，后续通过 `/task-orchestrator [相同需求]` 恢复。

## 3. 任务循环

对每个任务，执行**三阶段审查 + 自动重试**。

### 3a. 执行 chain

```
subagent: chain: [
  {agent: "implementer", task: "实现任务 N：[从计划文件中提取的完整任务描述]"},
  {agent: "spec-reviewer", task: "审查以下实现是否完整匹配设计文档：{previous}。对照 docs/superpowers/specs/ 中的设计规格，检查缺失和多余功能"},
  {agent: "code-reviewer", task: "审查以下实现：{previous}。检查代码质量、安全性和项目模式遵从"}
]
```

### 3b. 自动重试（最多 3 次尝试）

如果 chain 失败（任一 agent 未通过），**自动进入修复循环**，不上报给用户：

1. 取最后一个失败 agent 的审查反馈（spec-reviewer 或 code-reviewer 的失败原因）
2. 调用单独的子代理修复：
   ```
   subagent: 使用 implementer 修复以下审查反馈中指出的问题：
   
   审查反馈：{失败的审查结果}
   原始任务：{任务描述}
   ```
3. 修复后重新执行 3a 的完整 chain
4. 重复此流程，最多 3 次尝试

**只有全部 3 次尝试都失败时**，才暂停并展示选项：

> ⚠️ 任务 N 在 3 次尝试后仍未通过审查。已完成 N-1/Y 个任务。最后一次失败原因：[摘要]
> - **1** 手动重试（再做 3 次自动尝试）
> - **2** 跳过当前任务，继续下一个
> - **3** 重新规划（回到步骤 2）

### 3c. 进度与完成

规则：
- 逐个执行：完成一个任务及其全部审查后，再开始下一个
- 每个任务完成后报告进度（如 "✅ 任务 2/5 完成（1 次通过）" 或 "✅ 任务 2/5 完成（2 次尝试后通过）"）

所有任务执行完成后，输出：**✅ 步骤 3/4：所有任务执行完成，共 N 个任务**

## 4. 最终审查与汇总

所有任务完成后，执行最终审查：

```
subagent: 使用 final-reviewer 审查整个项目变更，检查所有需求是否满足、代码一致性、可合并性
```

如果 final-reviewer 失败，仍然展示步骤 3 中已完成的汇总结果（任务数、审查通过数），跳过最终审查意见，直接展示汇总。

审查完成后，汇总所有结果并展示：

> ## 📊 执行汇总
>
> | 项目 | 结果 |
> |------|------|
> | 设计文档 | `docs/superpowers/specs/<file>` |
> | 实现计划 | `docs/superpowers/plans/<file>` |
> | 任务完成 | X/Y |
> | 规格审查 | [通过数]/[总数] |
> | 代码审查 | [通过数]/[总数] |
> | 最终审查 | [意见摘要] |
>
> 下一步：
> - **1** 合并到主分支
> - **2** 创建 PR
> - **3** 继续修改
> - **4** 查看具体某个任务的细节

输出：**✅ 步骤 4/4：汇总完成**

## 中断恢复

编排器会在执行过程中自动将进度保存到 `.pi/task-orchestrator-state.json`，用于跨 session 恢复（best-effort）。同 session 内的中断恢复保证可用。

如果用户在执行过程中中途取消（Ctrl+C 或关闭会话），状态文件中记录：

- 已完成的任务列表及其结果
- 当前所在步骤
- 待执行的任务列表

下次用户重新执行 `/task-orchestrator [相同需求]` 时，优先检查状态文件并询问：

> 🔄 检测到上次未完成的任务编排。当前进度：步骤 X/4，已完成 N/Y 个任务。
> - **1** 从断点继续
> - **2** 重新开始（放弃之前的进度）

> ⚠️ 跨 session 恢复为 best-effort（依赖状态文件完整性），同 session 内保证可用。
